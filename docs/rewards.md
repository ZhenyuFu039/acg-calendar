# 嵌晶玉统计

时间轴最右列显示该活动可获得的嵌晶玉，顶部为当前版本的已核实小计。全部活动列表、活动详情及 Windows 桌面卡片也显示数量。使用的是用户提供的原始透明 PNG 图标。

统计活动潜在总奖励，不读取账号或已领取状态。完成标记、搜索、分类、日期范围与隐藏选项不改变版本总数。

## 程序规则

- `rules/endfield-cn.json` 的 `rewards` 配置控制数量匹配与每日/单次排除模式；使用整数，不做概率估算。
- 每个活动保留 `source.reward_lines`，每笔奖励保留公告 URL、标准化行号与原文。以版本、来源行和同一行的匹配位置生成奖励 ID，重复出现在不同日历行时只计一次。
- 活动兑换商店保留自己的截止时间，通过 `reward.shared_with` 关联活动奖励池，界面标为“共享”。危机合约和机密圣所各显示 2,000，版本总数只包含一次。
- 不把“3 轮换 × 3 关”乘到累计奖励上；两期独立赛季各计 300。密境行者分两批开放，共计公告写明的 1,200。
- 官方导览只读取 `item_diamond`。当前部分卡片 `quantity=1` 仅用于展示，不能代替公告总数。明确数量大于 1 才作为缺失数量的补充；冲突保留公告数并列入 `reward_summary.conflicts`。
- 每日/单次奖励缺少明确活动累计数量时保持未知，不靠活动天数估算。
- 未归属到日历活动的嵌晶玉原文保留在 `reward_summary.other_mentions`，显示原因和官方依据。
- `reward_summary.complete=false` 表示未承诺覆盖所有免费资源；`verified_total` 是已核实的小计。导出 JSON 同时包含逐笔明细、未知项目、单列来源和冲突。

此实现面向已验证的官方文本与导览配置。不 OCR 图片内的奖励表，也不自动解析所有单独活动新闻；官方未明确的数量需要后续公告补齐。
