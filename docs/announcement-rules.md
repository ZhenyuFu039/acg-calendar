# 终末地公告规律与 JSON 设计

本 Demo 使用两层 JSON：`rules/endfield-cn.json` 描述如何读取公告，`samples/endfield-cn-6094.parsed.json` 展示解析结果。JSON 是配置与数据；Python 程序执行解析和校验。

## 公告层次

实际样例：[「丹青渡」版本更新说明](https://endfield.hypergryph.com/news/6094)。

```text
版本更新说明
├── 更新维护时间
├── 全新寻访及申领
│   ├── 编号条目：万物更新
│   └── 编号条目：篆玉申领 ……
├── 全新活动
│   ├── 编号条目：烟火生缘
│   │   ├── 活动时间
│   │   ├── 活动内容更新时间
│   │   └── 活动说明
│   └── 编号条目：危机合约
│       └── 机密圣所开放时间（独立兑换条目）
└── 活动及玩法更新
    ├── 战争回响
    │   ├── 异想赛季
    │   └── 狂热赛季
    ├── 影拓丰碑更新节点
    │   └── 丰碑留名 · 魇林（独立限时活动）
    └── 密境行者更新节点
```

先按 `■` 识别章节，仅处理 JSON 白名单中的章节；再按编号拆活动，最后在每个活动块里识别时间与说明。解析器不会将整篇公告里的所有日期拼成一个区间。

`○` 表示玩法下的独立赛季。兑换商店时间和“同时开放……”的活动可以生成子条目，保留 `parent_title`。活动内容更新节点保存在 `phases`。

## 规则配置

`structure` 控制章节及标题规律，`time` 配置时间字段别名和维护引用，`classification` 控制活动子类型与说明字段。日期格式、章节名称、别名发生小变化时，可直接调整 JSON。

引入新的复杂语义结构时仍需要更新 Python，例如添加一种新的周期计算关系。配置文件不会执行代码，也不会自动生成猜测日期。

## 统一活动结构

```json
{
  "id": "稳定的活动标识",
  "version_id": "endfield-cn-6094",
  "title": "「卡莉的芳菲童话」拍照活动",
  "category": "event",
  "subtype": "拍照",
  "time_kind": "interval",
  "start": {
    "at": "2026-10-22T04:00:00Z",
    "state": "exact",
    "reference": null,
    "raw": "2026/10/22 12:00",
    "precision": "minute"
  },
  "end": {
    "at": "2026-11-04T20:00:00Z",
    "state": "exact",
    "reference": null,
    "raw": "2026/11/05 04:00",
    "precision": "minute"
  },
  "phases": [],
  "source": {
    "url": "https://endfield.hypergryph.com/news/6094",
    "time_label": "活动时间",
    "time_text": "2026/10/22 12:00 - 2026/11/05 04:00（服务器时间）"
  }
}
```

源码中的结果另含原文行号、完整活动块、说明、参与条件和解析警告。完整样例见 `samples/endfield-cn-6094.parsed.json`。

### 时间状态

| state | 含义 | 可用于精确截止提醒 |
| --- | --- | --- |
| `exact` | 公告给出明确日期和时间 | 是 |
| `estimated` | 从预计维护结束时间推导 | 否 |
| `confirmed` | 用户记录实际开服时间后关联 | 是 |
| `manual` | 用户主动校正 | 是 |
| `unknown` | 尚未提供可计算的日期 | 否 |

`reference` 支持：

- `maintenance_end`：本次维护结束。
- `next_maintenance_start`：后续版本维护开始。
- `recruitment_cycles`：若干次寻访后结束，保留原条件。
- `unpublished`：没有明确的结束时间。

所有可计算的 `at` 都保存为 UTC。国服原始时区为 UTC+8，浏览器以 IANA 时区和该事件的日期生成当地显示。不会用“纽约永远差 12 小时”的固定差值。

## 个人数据与采集结果

版本原始解析结果保存在 `versions`，个人修改保存在独立的 `local_state`。展示时依次应用：

1. 官方解析的明确日期或相对引用。
2. 实际开服记录，以及后续版本维护开始时间。
3. 个人对这个活动的手动校正。

活动 ID 由版本、章节、活动标题和子条目身份生成，不依赖正文行号；插入导航文字或说明段落不会直接导致完成标记丢失。标题实质性改变时仍可能产生新 ID，这需要后续完善身份匹配。

## 提醒与覆盖范围

提醒以当前有效截止时间、活动 ID 和提前量组成持久去重键。已完成、忽略、关闭提醒、时间顺序异常、仅有更新节点、预计截止或截止待定的条目跳过。

进入多个提前窗口时仅补发当前最紧急的一档；截止时另有一次到期提醒。已过期超过 6 小时的记录不会因重新启动而集中补发。修改截止时间后使用新的去重键。

采集器验证过官网当前使用的公开接口，但这些不是官方保证长期兼容的开发者 API。每轮最多读取官网列表 3 页（每页 20 条）、两篇版本更新说明及三篇版本导览新闻，具体数量可在规则 JSON 调整。

## 官方更新公告与版本导览

采集路径为：官方新闻列表 → 版本更新说明；官方新闻列表 → 新版本导览上线新闻 → 新闻内的官方专题入口 → 专题引用的版本脚本 → 国服结构化活动配置与素材。

程序仅静态解码脚本中 `JSON.parse` 的字符串数据，不执行官网 JavaScript，也不加载登录、领赏、统计或第三方脚本。只取 `timeByServer.cn`，按 UTC+8 转换存储。

- 导览内的中文版本名必须与新闻标题及对应更新公告一致。`latest` 的内容一旦换版，拒绝配给旧版日历。
- 成功取得的版本名、版本标识、脚本 URL/校验值、9 类活动配置及来源新闻写入 `data/sources/briefings/`。同一带内容哈希的脚本不重复下载；专题暂不可用时可以保留历史快照。
- 活动名称精确匹配，独立赛季可关联其父玩法的图片；父玩法多年前的上线时间不会覆盖当期赛季时间。
- 公告已明确的起止时间优先；导览若提供不同的精确值，将两者写入 `event.briefing.conflicts`，保留公告值并提示核对。
- `startsAfterUpdate=true` 不使用原始 `openTime` 充当实际开服；`endTimeDisplay=beforeUpdate` 或 `alwaysAvailable` 不使用原始 `closeTime` 创建精确截止。
- 仅对公告未公布、没有维护/次数关联含义的有效区间端点，允许用导览的明确日期补齐，并标记 `reference=briefing_explicit`。个人手动校正仍最后应用。
- 导览比更新公告先发布时，先缓存并列入 `briefing_previews`；更新公告出现后自动合并。无法匹配的导览条目记录在 `unmatched_activities`，不擅自生成当期活动。
- 界面同时提供版本更新公告、导览上线新闻与专题入口，JSON 和日历导出保留来源。

目前不接入第三方站点；素材仍由原权利人持有，缓存目录不加入 Git。
